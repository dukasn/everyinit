# The EVIN Book

EVIN is the workflow engine for software repositories. It turns the commands
and delivery routines around a codebase into a declared task graph under
`.evin/`. The same target can then be run by a developer, a Git hook, or CI.

This Book is the practical path through that model. It explains why each part
exists, shows complete configurations, and points to the Technical Reference
when you need the exact accepted fields.

## The mental model

| Layer | What you declare | What EVIN does |
| --- | --- | --- |
| Workspace | Identity, stages, shared values, modules, and tasks | Loads the repository workflow from `.evin/workspace.flow` |
| Task graph | Named tasks and `needs` edges | Selects a task, stage, or hook target and resolves its prerequisites |
| Runtime | `run` commands | Executes portable automation through ESH |
| Environment | `.env`, workspace/module variables, presets, and a schema | Builds the environment exposed to each task and redacts declared secrets |
| Git integration | Hook triggers and Git rules | Installs hook shims and enforces supported repository policies |
| Delivery | Built-in actions | Produces docs, versions, changelogs, archives, and release commits inside the graph |

> [!IMPORTANT]
> A stage groups tasks and gives the group a runnable name. It does not create
> an ordering edge by itself. Use `needs` whenever one task must finish before
> another starts.

## Reading path

1. [Installation](/book/installation) installs the source build, verifies the
   CLI, and explains what `evin init` creates.
2. [First workspace](/book/first-workspace) builds a small check-and-test graph
   and exercises task, stage, dry-run, and verbose execution.
3. [Workspaces](/book/workspaces) covers every layer of the repository model:
   modules, values, environments, execution modes, and watch tasks.
4. [Pipelines and hooks](/book/pipelines-and-hooks) connects the graph to Git
   and explains how synchronized hooks invoke the same targets.
5. [Documentation site](/book/documentation-site) uses the documentation
   action as a complete built-in delivery workflow.

## Guide or reference?

Use the Book when you are deciding how to model work. Use the
[Technical Reference](/reference) when you need field types, defaults,
validation rules, output names, or exact CLI syntax.
