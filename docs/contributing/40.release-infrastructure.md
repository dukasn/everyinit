# Release infrastructure setup

The release workflows use Cloudflare R2 for the public download mirror. Pull
request candidates go to the `unstable` lane. After a tagged candidate merges
into `main`, the workflow copies the same Evin and ESH tar.gz archives into the
`canary` lane and updates the shared canary manifest.

This page covers one-time account setup. It does not ask a pull request job to
receive Cloudflare credentials. The build workflow uploads an Actions artifact
without secrets; a trusted `workflow_run` job signs and uploads it.

## Cloudflare account and buckets

The Cloudflare account must contain an active `everyinit.dev` zone. The
Workers configuration binds two private R2 buckets:

| Bucket | Contents | Writer |
| --- | --- | --- |
| `everyinit-preview-artifacts` | Immutable `unstable` candidate archives, metadata, and `channels/unstable.json` | GitHub's `unstable` environment token |
| `everyinit-artifacts` | Immutable `canary` archives, metadata, and `channels/canary.json` | GitHub's `release` environment token |

Create the buckets in the same Cloudflare account as the Workers. With the
repository's pinned Wrangler installed, the commands are:

```sh
corepack npm exec -- wrangler login
corepack npm exec -- wrangler r2 bucket create everyinit-artifacts
corepack npm exec -- wrangler r2 bucket create everyinit-preview-artifacts
corepack npm exec -- wrangler r2 bucket list
```

Keep public `r2.dev` bucket URLs disabled. The `get.everyinit.dev` and
`dl.everyinit.dev` Workers are the only public serving layer; this keeps the
mirror's routing, cache headers, and content-type behavior consistent.

The release publisher uses Wrangler's Cloudflare API, not the R2 S3 API. Create
two **account API tokens** with `Workers R2 Storage Bucket Item Write`, each
scoped to just one bucket: the preview token for `everyinit-preview-artifacts`
and the release token for `everyinit-artifacts`. That bucket-item permission
allows object read, write, and list operations. Do not use an R2 S3 Access Key
and Secret Access Key in these workflow secrets; those credentials are for
S3-compatible clients. See Cloudflare's [R2 token permission
reference](https://developers.cloudflare.com/r2/api/tokens/) and [API token
permission list](https://developers.cloudflare.com/fundamentals/api/reference/permissions/).

## Connect the Workers to the public hostnames

`infra/get/wrangler.toml` attaches the installer Worker to the custom domain
`get.everyinit.dev`. `infra/mirror/wrangler.toml` attaches the mirror Worker to
`dl.everyinit.dev`. A custom domain makes the Worker the origin for the whole
hostname; Cloudflare creates the DNS record and certificate. Confirm that the
zone is active and that neither hostname has a conflicting DNS record or
Worker route before deploying. Cloudflare's [Custom Domains
guide](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)
describes migration from an existing route or CNAME.

Deploy each Worker once from a trusted checkout:

```sh
corepack npm ci
corepack npm exec -- wrangler login
cargo evin-dev run infra:deploy:workers
```

The mirror Worker requires both R2 buckets to exist before its first deploy.
The Wrangler bindings in the config file do not make either bucket public. In
local development, Wrangler uses local R2 simulation unless explicitly run with
remote bindings; keep local release rehearsals on local storage.

There is currently no GitHub Actions workflow that deploys Worker code. The
release workflows upload mirror objects; the `infra:deploy` Flow namespace is
an intentional manual deploy path. Deploy Worker changes from a trusted
workstation with `wrangler login`. If Worker deployment is automated later,
give it a separate deploy token rather than reusing either release upload
token. A production deploy token needs permission to edit the Worker and to
manage the two custom domains. See Cloudflare's [Workers authorization
guide](https://developers.cloudflare.com/workers/authorization/workers/).

## GitHub environments and secrets

Create two GitHub Actions environments in repository Settings, Environments.
Add these environment secrets with the exact names used by the workflow files:

| Environment | Secret | Value |
| --- | --- | --- |
| `unstable` | `EVERYINIT_RELEASE_SIGNING_KEY` | Ed25519 PKCS#8 private key matching `infra/get/release-key.pub` |
| `unstable` | `CLOUDFLARE_ACCOUNT_ID` | Cloudflare account ID that owns both R2 buckets |
| `unstable` | `CLOUDFLARE_PREVIEW_API_TOKEN` | Account API token scoped to `everyinit-preview-artifacts` |
| `release` | `EVERYINIT_RELEASE_SIGNING_KEY` | The same Ed25519 private key, stored as a protected environment secret |
| `release` | `CLOUDFLARE_ACCOUNT_ID` | Cloudflare account ID that owns both R2 buckets |
| `release` | `CLOUDFLARE_API_TOKEN` | Account API token scoped to `everyinit-artifacts` |

Use the same release signing key in both environments. The installer pins its
public key, and both mirror channels must have metadata that the installed
verifier accepts. Keep the private key out of the repository and never expose
it to the pull request build job.

Restrict both environments to deployments from `main`. Do not require a human
reviewer for `unstable`; its trusted job must run automatically after candidate
builds so the check can finish before merge. You can require reviewers for the
`release` environment if you want a human approval between merge and canary
publication. GitHub environments apply their protection rules before exposing
environment secrets to the job; see [Managing deployment
environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments).

The workflows declare their own `GITHUB_TOKEN` permissions. No personal
GitHub token is needed. The release job requests write access to repository
contents to create or update GitHub Releases. The preview job requests read
access to the source run artifact and write access to its check run.

## Protect `main` and seed the preview check

In GitHub repository Settings, create a ruleset for `main` that requires pull
requests and the repository's normal CI checks. Also require the custom check
named `Unstable preview`. It is emitted by
`.github/workflows/release-preview.yml` and succeeds on ordinary pull requests
that are not release candidates.

Ordinary pull requests keep that successful check when the candidate build is
skipped. A labeled candidate or changed workspace version still requires a
successful build and preview. Because this trusted workflow runs from `main`,
fixes to the workflow must reach `main` before a candidate rerun can use them.

The check name becomes selectable after the workflow has emitted it at least
once. Let the workflow run on a non-release pull request, then add `Unstable
preview` to the required checks before opening or merging the first release
candidate. GitHub rulesets let you require status checks before merge; see the
[ruleset status-check guide](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

Create the repository label `release-candidate`. Add it to a release PR to
build its tagged artifacts and publish the unstable preview. The preview
workflow also detects a changed release version if the label is removed, so
removing the label cannot turn a failed versioned candidate into an ordinary
passing PR.

Allow merge commits for release PRs and use a merge commit for them. The
candidate tag points to the PR head commit; the main-branch publisher finds
that exact tagged commit when it becomes reachable from `main`. Squash or
rebase merging can discard that tagged commit and prevent the release job from
finding the candidate.

The repository can keep the default `GITHUB_TOKEN` restricted to read-only.
Each workflow declares only the permissions it needs at the workflow or job
level. GitHub documents these settings under [workflow
permissions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication).

## Verify the setup

After the buckets and custom domains are configured:

1. Deploy both Workers and confirm `https://get.everyinit.dev/evin` returns the
   installer script.
2. Confirm `https://dl.everyinit.dev/canary.json` and
   `https://dl.everyinit.dev/unstable.json` reach the mirror Worker. A `404`
   is expected until the corresponding channel manifest has been published;
   a DNS failure or Cloudflare `522` means the custom domain or Worker route is
   not connected correctly.
3. Open an ordinary pull request and verify that `Unstable preview` completes
   successfully. Then make it a required check in the `main` ruleset.
4. Open a release candidate PR with a new annotated `v<version>` tag, a changed
   release label, its changelog entry, and the `release-candidate` label. The
   workflow must fetch and verify both tar.gz files through
   `dl.everyinit.dev` before that check succeeds.
5. After merge, confirm the `release` job publishes GitHub Releases, uploads
   canary objects, and moves `canary.json` only after both binaries are ready.

The first preview cannot publish until the `unstable` environment, bucket,
token, and public mirror Worker are in place. Do not mark the preview check as
optional to work around missing Cloudflare setup; the merge gate is intended
to prove that the public download path works before publishing canary.
