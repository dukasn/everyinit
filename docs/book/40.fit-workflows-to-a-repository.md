# Fit workflows to a repository

Start with one `.evin/workspace.flow`. You do not need to split configuration
just because Evin supports modules and namespaces. Add structure when it
helps people find, own, or run a group of tasks.

## Keep shared work at the root

Checks that apply to the whole repository belong in the root workspace:

```flow
workspace:
  name: storefront
  version: "1.0.0"
  modules: [apps/web, crates/api]

stages: [Check, Test, Build]

tasks:
  verify:
    stage: Check
    description: "Run repository-wide checks"
    run: npm run verify
```

The root workspace remains the place for shared stages and cross-project
targets. A module is useful when a directory has its own repeatable work and
should be runnable as a unit.

## Give a project area its own tasks

For example, `apps/web/.evin/module.flow` can define frontend tasks:

```flow
module:
  name: web

tasks:
  test:
    stage: Test
    description: "Run the web application tests"
    run: npm test

  build:
    stage: Build
    needs: [test]
    run: npm run build
```

Run the module task as `evin run web:build`. Module tasks use the module
directory as their default working directory, so `npm test` runs in
`apps/web`. They use the stages declared by the root workspace. Root tasks run
from the workspace root by default.

## Use namespaces for related routines that share a module

A module does not need to become a separate module for every task group. Use
an included namespace when several routines belong together but share the same
project area—for example, database maintenance or release preparation.
Large namespaces can include child namespace files from a directory so related
task groups stay scoped under one root, such as `release:ci:*` and
`release:pub:*`. A child file can also declare the same namespace name as its
parent; when it is explicitly included, its tasks join that same scope. This
lets you split a large workflow into files like `release/proposal.flow` and
`release/artifacts.flow` while keeping tasks addressable as `release:bump` or
`release:archives`. Unrelated files that independently claim the same scope
still trigger a duplicate namespace error.

```flow
# .evin/workspace.flow
workspace:
  name: storefront
  version: "1.0.0"
  include: [.evin/maintenance.flow]
```

```flow
# .evin/maintenance.flow
namespace:
  name: maintenance
  description: "Repository maintenance workflows"

tasks:
  audit:
    stage: Check
    description: "Audit repository dependencies"
    run: npm audit
```

That task is selected as `evin run maintenance:audit`. Namespaces organize
tasks; modules give a directory its own task scope and default working
directory.

## Keep configuration values in the right place

Use workspace or module values to share action inputs such as an artifact
directory or package name. Use environment configuration for values that
commands need in their process environment. For secrets, configure the
environment through the repository's secret-management mechanism instead of
committing secret values.

Do not split files or define shared values before they solve a real repetition
or ownership problem. For exact include rules, qualification, precedence, and
accepted fields, see the [module](/reference/module-configuration),
[namespace](/reference/namespace-configuration), and
[environment](/reference/environment-configuration) references.
