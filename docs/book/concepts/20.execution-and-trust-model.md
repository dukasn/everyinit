# Execution & trust model

Introducing a workflow engine into a repository touches the same surface as
build scripts, credentials, Git hooks, and release automation. You should be
able to verify what Everyinit will run, what it can access, how it handles
failures, and how to remove it before running a single task.

> [!IMPORTANT]
> Everyinit provides workflow orchestration and process-group supervision, not
> security sandboxing. Treat `.flow` manifests and `.esh` scripts in a cloned
> repository with the same care you give a `Makefile`, `build.rs`, or
> `package.json` lifecycle script: inspect them before running tasks.

## Inspect before executing

Evin separates static configuration analysis from task execution so you can
audit an unfamiliar workspace without running subprocesses or modifying tracked
files:

- **`evin check`** parses workspace, module, namespace, environment, and policy
  manifests, checks the task graph for missing dependencies or cycles, and
  validates built-in action inputs—never executing tasks, hooks, or shell steps.
- **`evin list`** prints every root and module-qualified task alongside the
  manifest file path that defines it.
- **`evin explain <target>`** resolves a task, stage, or Git hook using the
  exact registry `run` uses, then prints its stage, working directory,
  dependencies, required environment variable *names* (never values), and
  summarized steps.
- **`evin run <target> --dry-run`** and **`evin sync --dry-run --verbose`**
  preview planned commands, built-in action plans, and proposed Git hook shims
  without running shell steps.

**Filesystem boundary during inspection:** `list`, `explain`, and `check` only
read workspace manifests, `.env`, and (when `.evin/release-lock.json` is
present) local Git index metadata. `run --dry-run` skips writing
`.evin/trace.json`, and `sync --dry-run` skips writing `.git/hooks/*` or staging
lock changes. By contrast, `evin init` is an explicit scaffolding command and
creates starter files when invoked.

When you want runtime telemetry during or after a real execution, `--debug`,
`--events ndjson`, and `.evin/trace.json` record resolved DAG edges, injected
environment key names, subprocess timings, and Chrome/Perfetto waterfall traces.

```sh
evin check
evin explain verify
evin run verify --dry-run
evin sync --dry-run --verbose
```

## Process privileges and non-isolation

Evin and ESH run in user space under the invoking operating-system user:

- **No privilege escalation by Evin:** Evin installs into `~/.local/bin` by
  default, never requests root privileges itself, and runs no persistent
  background daemon (`evin lsp` communicates over standard input and output only
  while an editor session is open). Task commands you run can still invoke
  programs that request or hold elevated privileges, such as `sudo`, setuid
  binaries, or container sockets.
- **Supervision, not sandboxing:** Evin does not place tasks inside containers,
  Linux namespaces, `chroot` jails, `seccomp` filters, or network firewalls. A
  running task has the same filesystem, network, SSH agent, and credential
  access as any command you run directly in your terminal.
- **Working directory scoping:** Root tasks execute from the workspace root by
  default, and module tasks execute from their module directory unless `cwd`
  selects another path.
- **Session and process-group boundaries:** On Linux, automated task commands
  spawn in a dedicated session and process group (`setsid`), detaching child
  processes from the caller's controlling terminal. Because cleanup targets that
  process group rather than a kernel cgroup or PID namespace, a descendant
  process that explicitly creates its own session or process group (`setsid` or
  `setpgid`) may not be terminated when Evin cleans up the group.

## Environment inheritance and secrets

Child processes do not inherit the caller's raw shell environment unchecked.
Evin clears the child environment (`env_clear()`) and constructs each task's
process variables from declared sources: the workspace `.env` file, workspace
and module `env` maps, `.evin/environment.json` defaults, and permitted host
variables.

Understand two defaults when reviewing or authoring sensitive workflows:

- **Default pool vs. explicit scoping:** A task that omits both `env` and
  `presets` receives the full resolved workspace variable pool plus a small host
  safelist (`PATH`, `HOME`, `USER`, `SHELL`, and `TERM`). To restrict a task to
  only the variables it needs, declare `presets` or an `env` key list, and set
  `pure: true` when you also want to drop the default host safelist:

  ```flow
  tasks:
    publish-docs:
      stage: Publish
      presets: [ci]
      pure: true
      env: [PATH, CLOUDFLARE_API_TOKEN]
      run: ./scripts/deploy.sh
  ```

- **Scopes and stage filters:** In `.evin/environment.json`, `scopes:
  ["Internal"]` keeps a variable available to Evin templates without injecting
  it into child process environments, and `stages` restricts which stages may
  receive a variable at all.
- **Secret redaction and its limits:** Variables marked `type: secret` in
  `.evin/environment.json`, `.env` entries, common secret-named host variables,
  and secret-named `EVIN_STATE` outputs of at least four characters are replaced
  with `***` in captured task output. Redaction protects terminal logs and UI
  streams from accidental leaks; it cannot stop a task command from reading
  files, sending secrets over the network, or exposing values passed on a
  process command line (`/proc/<pid>/cmdline`). See the
  [environment reference](/reference/environment-configuration) and
  [diagnostics reference](/reference/diagnostics-and-output#redaction-boundary).

## Execution, failure, and cancellation

Evin's pipeline engine follows deterministic rules before and during a run:

1. **Preflight validation before step one:** Before running any task in the
   selected target graph, Evin validates every native `uses:` / `with:` action
   contract and trailing CLI flag. Configuration errors abort during
   **Resolving configuration** before any shell step starts.
2. **Explicit dependencies over list order:** Stage names (`Check`, `Build`,
   `Test`) group tasks into selectable targets; stage list order never creates
   hidden dependencies. Execution order comes strictly from `needs` edges.
3. **Sequential by default:** Without `workspace.execution: parallel` or
   `--parallel`, ready tasks run one at a time. Steps within a single task
   always run sequentially and stop on the first non-zero exit status.
4. **Fail-fast propagation across parallel tasks:** When a task fails during
   parallel execution, Evin immediately cancels its run token, aborts in-flight
   sibling tasks, skips all unstarted dependents, and exits with a non-zero
   status.
5. **`Ctrl+C` and process-group cleanup:** Interrupting `evin run` cancels the
   active graph, allows a brief grace window to record task telemetry, and
   signals each supervised child process group (`SIGTERM` followed by `SIGKILL`
   after the grace timeout) before exiting. Descendants that escaped into a
   separate session or process group are not tracked after exit.

### Failure does not imply rollback

Evin coordinates execution order, failure propagation, and process-group
cancellation. It does **not** provide transactional rollback: filesystem edits,
Git commits or tags, network requests, published packages, or other external
side effects completed before a step failed remain in place unless your own
scripts or recovery tasks clean them up.

## Reversibility

Everyinit is designed for reversible integration rather than ecosystem lock-in,
with migration cost proportional to which features you adopt:

- **Low-friction workflow layer:** Tasks in `.evin/workspace.flow` that invoke
  your existing `cargo`, `npm`, `python`, or shell commands leave those tools
  directly runnable without Evin. Removing `.evin/` restores the repository to
  its prior state.
- **Non-destructive Git hooks:** `evin sync` wraps generated hook shims between
  `# --- EVIN Start ---` and `# --- EVIN End ---` markers inside
  `.git/hooks/pre-commit`, `commit-msg`, and `pre-push`, leaving commands
  outside those markers intact.
- **Native actions and ESH scripts:** Adopting built-in `evin/*@v1` actions
  (such as docs compilation, packaging, or release sync) or writing substantial
  automation in `.esh` replaces custom glue with Evin-specific contracts; moving
  away later requires porting those steps to another tool or shell.

Step-by-step cleanup instructions for both a repository and local CLI binaries
are documented in [removing Everyinit](/book/installation#removing-everyinit).

## Compatibility and upgrades

Everyinit is in active canary development. Configuration schemas use explicit
version headers (`#!evin/v1` and versioned JSON `$schema` URIs), while CLI flags,
action contracts, and runtime behaviors can still evolve between releases
without legacy compatibility shims. For shared repositories and CI runners, pin
an explicit CLI release with `--version VERSION` during
[installation](/book/installation) and review release notes before upgrading.

## Release integrity and verification

Everyinit's distribution pipeline lets you verify binary artifacts before
running them:

- **Ed25519-signed release manifests:** Every release publishes `SHA256SUMS` and
  an Ed25519 signature (`SHA256SUMS.sig`) verified against the public key pinned
  at `infra/get/release-key.pub` in the repository. Both the release installer
  and manual OpenSSL verification check the signature before extracting any
  archive; see [verify a release](/book/installation#verify-a-release).
- **Exact-SHA CI and dependency audit gates:** Release artifacts are built from
  public GitHub Actions workflows only after exact-commit Linux validation
  (workspace tests, binary E2E, distribution rehearsal, and `cargo-audit` /
  `npm audit` checks) succeeds on `main`.
- **OIDC trusted publishing:** Both the `everyinit` npm package and Visual
  Studio Marketplace extension publish through GitHub Actions OIDC trusted
  publishing tied to `release.yml`, avoiding long-lived registry tokens.
- **Source builds and vulnerability reporting:** You can compile `evin` and
  `esh` directly from a locked Git tag with `cargo install --locked`. Suspected
  security issues can be reported privately through the
  [security policy](https://github.com/dukasn/everyinit/blob/main/SECURITY.md).
