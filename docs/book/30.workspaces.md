# Workspaces

The workspace manifest is both an index and an execution contract. It names
the repository, registers modules, defines selectable stages, and owns the root
tasks from which EVIN builds a directed acyclic graph.

## Workspace anatomy

```yaml
workspace:
  name: shop
  version: "1.4.0"
  rules: .evin/gitrules.yaml
  execution: linear
  modules:
    - crates/api
    - apps/web

stages: [Check, Build, Test, Publish]

values:
  archive_name: shop

env:
  RUST_BACKTRACE: "1"

tasks:
  check-license:
    stage: Check
    run: cargo deny check licenses
```

| Section | Role |
| --- | --- |
| `workspace` | Required identity and workspace-wide execution/discovery settings |
| `stages` | Required list of valid stage names; stage names begin with an uppercase letter |
| `tasks` | Optional map of lowercase task identifiers to task declarations |
| `values` | String values available to built-in action templates such as `${archive_name}` |
| `env` | Workspace environment values merged over values loaded from `.env` |

Task names accept lowercase ASCII letters, digits, and hyphens. Stage names
begin with an uppercase ASCII letter and otherwise contain letters or digits.
Unknown YAML fields are rejected.

## Model ordering with `needs`

Consider three tasks that are ready at different points:

```yaml
tasks:
  lint:
    stage: Check
    run: cargo clippy -- -D warnings

  unit-test:
    stage: Test
    run: cargo test --lib

  package:
    stage: Build
    needs: [lint, unit-test]
    run: cargo build --release
```

`package` becomes ready only after both prerequisites succeed. The relative
position of `Check`, `Test`, and `Build` in `stages` does not add edges.

> [!WARNING]
> A cycle in `needs`, an unknown dependency, or a task assigned to an
> undeclared stage fails during graph validation before task execution begins.

## Choose an execution policy

The workspace defaults to `linear`: only one ordinary ready task runs at a
time. Set `workspace.execution: parallel` to dispatch all ready tasks
concurrently, or override one invocation:

```esh
evin run Check --parallel
evin run Check --sequential
```

A task with `parallel: true` is individually eligible for concurrent dispatch
even when the workspace is linear. Dependencies are always respected.

## Use one command or ordered steps

```yaml
tasks:
  verify:
    stage: Check
    description: "Run all source checks"
    cwd: crates/core
    steps:
      - run: cargo fmt -- --check
      - run: cargo clippy -- -D warnings
```

Steps within one task run in declaration order and stop on the first failure.
Each step contains either `run` or `uses`; a `uses` step may include `with`.
Repository commands execute through ESH and `cwd` is resolved relative to the
workspace root.

## Share values and action outputs

Values configure actions without pretending to be process environment
variables. Outputs from a prerequisite action use `${task.output}` syntax:

```yaml
values:
  artifact_dir: dist

tasks:
  bump:
    stage: Publish
    steps:
      - uses: evin/version-bumper@v1
        with:
          initial_version: "0.1.0"

  package:
    stage: Publish
    needs: [bump]
    steps:
      - uses: evin/archive@v1
        with:
          path: "${artifact_dir}/app-${bump.version}.tar.gz"
          include: [target/release/app]
```

Only outputs from declared prerequisites are available. Module values override
workspace values, and task `values` override both for that task.

## Split a monorepo into modules

Register each module directory in the root manifest:

```yaml
workspace:
  name: shop
  version: "1.4.0"
  modules: [crates/api, apps/web]

stages: [Check, Build, Test]
```

Then place `crates/api/.evin/module.yaml` beside the module's code:

```yaml
module:
  name: api

env:
  API_LOG: debug

values:
  package_name: shop-api

tasks:
  test:
    stage: Test
    run: cargo test
```

The task is invoked as `evin run api:test`, and its default working directory
is `crates/api`. A module-local `needs: [test]` is automatically qualified as
`api:test`. Prefix a root dependency with the workspace name when a local task
would otherwise shadow it, for example `needs: [shop:lint]`.

## Group logical workflows into namespaces with `include`

Not every group of related tasks belongs to a separate source directory.
Specialized workflows—such as release gates, database migrations, or
maintenance routines—can be factored into dedicated namespace files under
`.evin/`:

```yaml
# .evin/workspace.yaml
workspace:
  name: shop
  version: "1.4.0"
  include:
    - .evin/release.yaml
```

Define the tasks in `.evin/release.yaml`:

```yaml
# .evin/release.yaml
namespace:
  name: release
  description: "Release engineering and distribution pipelines"

env:
  RELEASE_CHANNEL: canary

tasks:
  doctor:
    stage: Publish
    description: "Verify prerequisite tools"
    run: cargo run --locked -p esh -- scripts/release/doctor.esh

  clean:
    stage: Publish
    description: "Require a clean checkout"
    run: cargo run --locked -p esh -- scripts/release/preflight.esh

  verify:
    stage: Publish
    description: "Validate source release gate"
    needs:
      - release:clean
      - verify
    run: git diff --check
```

Tasks are invoked as `evin run release:doctor` and run from the workspace root
by default. Dependencies in `needs` use explicit task names (such as
`release:clean` or root `verify`) to keep prerequisite edges unambiguous across
the workspace.

A module can also organize its own internal routines across separate files by
specifying `include:` in `.evin/module.yaml`. Tasks included by a module run
from that module's directory by default.

## Activate a watched workflow

Watch mode is task configuration, not a CLI switch:

```yaml
tasks:
  check:
    stage: Check
    watch:
      paths: [src/**, Cargo.toml]
      ignore: [target/**]
      debounce: 300ms
    run: cargo check
```

Running `evin run check` executes once, watches the declared relative patterns,
and reruns after a debounced change. `debounce` accepts positive integer
milliseconds (`300ms`) or seconds (`2s`). Absolute paths and patterns
containing `..` are rejected.

> [!NOTE]
> EVIN also watches the workspace, environment, Git-rules, and relevant module
> configuration used by the selected graph so configuration changes can
> re-resolve the session.

See the [workspace](/reference/workspace-configuration),
[module](/reference/module-configuration),
[namespace](/reference/namespace-configuration), and
[environment](/reference/environment-configuration) references for the exact
schemas.
