# Namespace configuration

> **RFC-4515 · Implemented Interface**
> Source types: `NamespaceFlow` and `NamespaceConfig`

A namespace file organizes logical workflow tasks (such as release routines, database migrations, package bundling, or maintenance checks) into a dedicated Flow document without requiring a separate physical codebase directory or submodule.

Namespace files are loaded when registered in `workspace.include` (or `module.include`). A namespace can include child namespace files to keep large task groups in a directory.

## Root schema

````lsp
target: [namespace]
language: flow
title: Namespace configuration
synopsis: "#!evin/v1\nnamespace:\n  name: release\n  description: \"Release engineering and distribution pipelines\"\n\nenv:\n  RELEASE_CHANNEL: canary\n\nvalues:\n  archive_prefix: evin\n\ntasks:\n  bump:\n    stage: Publish\n    steps:\n      - uses: evin/version-bumper@v1"
summary: Define namespace identity, description, inherited environment variables, template values, and tasks.
category: configuration
---
An included Flow document organizing workflow tasks into a logical namespace.

Namespace files allow modularizing workspace tasks into specialized files (e.g. `.evin/release.flow`, `.evin/packages.flow`) without needing physical code modules.

### Root Sections

| Key | Type | Required | Purpose |
| --- | --- | --- | --- |
| `namespace` | object | yes | Namespace identifier and human-readable description. |
| `include` | list or map of paths | no | Child namespace Flow files, resolved relative to this file (alias `includes`). |
| `tasks` | map of tasks | no | Tasks defined within this namespace. |
| `env` | map of strings | no | Environment variables inherited by all tasks in this namespace. |
| `values` | map of strings | no | Template values available to action configurations in this namespace. |
````

### Namespace metadata fields

````lsp
target: [namespace, name]
language: flow
title: Namespace name
synopsis: "name: release"
summary: Prefix identifier prepended to every task declared in this namespace document.
category: configuration
---
Specifies the namespace prefix prepended to every task defined in this file.

For example, with `name: release`, a task declared as `clean` is addressable as `release:clean`.
````

````lsp
target: [namespace, description]

````


````lsp
target: [namespace, tasks]
language: flow
title: Namespace tasks
synopsis: "tasks:\n  clean:\n    stage: Publish\n    run: cargo clean\n  bump:\n    stage: Publish\n    needs: [clean]\n    steps:\n      - uses: evin/version-bumper@v1"

---
Defines tasks owned by this namespace. Tasks use the standard task schema (`run`, `steps`, `needs`, `stage`, `env`, `presets`, `cwd`, etc.) and are qualified with `<namespace-name>:<task-id>`.
````

## Schema

```flow
#!evin/v1
namespace:
  name: release
  description: "Release engineering and distribution pipelines"

env:
  RELEASE_CHANNEL: canary

values:
  archive_prefix: evin
  staging_dir: "dist/release-stage"

tasks:
  clean:
    stage: Publish
    description: "Require a clean working tree"
    steps:
      - run: cargo run --locked -p esh -- scripts/release/check/doctor.esh

  bump:
    stage: Publish
    description: "Calculate and apply the next canary version"
    needs:
      - release:clean
      - verify
    steps:
      - uses: evin/version-bumper@v1
        with:
          initial_version: "1.0.0-canary.100"
          channel: canary
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `namespace.name` | string | yes | Namespace prepended to every task in this file (e.g. `release:clean`) |
| `namespace.description` | string | no | Human-readable UI and catalog summary shown in `evin list` |
| `include` | list or map | no | Nested namespace files; children are qualified beneath this namespace |
| `env` | string map | no | Environment variables inherited by all tasks in this namespace |
| `values` | string map | no | Document-level action-template values available to tasks in this namespace |
| `tasks` | task map | no | Map of task declarations using the standard task schema |

Unknown fields are rejected.

## Inclusion and nested namespaces

Namespace files can be included by both the root workspace and individual modules using either list or map format:

### In `workspace.flow`
```flow
workspace:
  name: main
  version: "1.0.0"
  include:
    - .evin/release.flow
    - .evin/maintenance.flow
    - .evin/packages.flow
```

Alternatively, use a map to assign or override the namespace prefix explicitly:

```flow
workspace:
  name: main
  version: "1.0.0"
  include:
    release: .evin/release.flow
    ops: .evin/maintenance.flow
```

### In `module.flow`
```flow
module:
  name: api
  include:
    - .evin/routes.flow
    - .evin/db.flow
```

Paths in `module.include` resolve relative to the module directory. If the namespace name matches the module name (e.g. `api`), tasks are prefixed as `api:<task>`. If a distinct sub-namespace is used (e.g. `routes`), tasks are prefixed as `api:routes:<task>`.

The alias `includes` is also accepted.

A namespace can include child namespace files using the same list or map syntax. Paths resolve relative to the including namespace file. Child names are appended to the parent scope, and environment variables and template values flow down to children; a child can override an inherited key.

```flow
# .evin/release.flow
namespace:
  name: release
include:
  - release/rehearsal.flow
  - release/proposal.flow
  - release/artifacts.flow
  - release/ci.flow
  - release/pkg.flow
```

Files declaring `namespace.name: release` contribute tasks to the existing `release:<task>` scope; files declaring `ci` or `pkg` become `release:ci:<task>` and `release:pkg:<task>`.

### Split one namespace across files

Namespace names normally identify one namespace in the workspace. There is one deliberate exception: a namespace may explicitly include another namespace file that resolves to the same full scope. Those documents are treated as fragments of the same namespace, so you can move a task group into another file without inventing an extra scope or renaming its tasks.

For example, `.evin/release.flow` can include `release/proposal.flow`, whose `namespace.name` is also `release`. A `bump` task in that file remains `release:bump`. Another included file can declare `namespace.name: ci`, making its `require` task `release:ci:require`. This makes it practical to organize a large release pipeline into a directory by lifecycle or responsibility while keeping existing task references stable.

The exception requires an explicit namespace include connecting the documents at the same scope. Two independently included files that happen to resolve to the same namespace still produce a duplicate-namespace diagnostic. Nesting is for organizing task documents; a module remains the construct for a project directory with its own default working directory and optional version.

For distro packages, register a normal namespace file such as
`.evin/packages.flow`; it contains shared `values` and standard
`evin/archive@v1` tasks with inline `with.package` objects. It is not a
separately discovered metadata file. See the Archive action reference for the
package schema and per-format examples.
