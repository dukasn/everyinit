# Contribution opportunities

These starter projects connect a concrete outcome to the code that owns it.
They are proposals, not assigned issues. Check the
[open issues](https://github.com/dukasn/everyinit/issues) before you start. If
an idea needs a larger design discussion, open an issue with the problem you
want to solve and the result you have in mind.

## Add an ESH automation recipe

Write a complete ESH script for a small project task you have encountered,
such as preparing release data or checking project files. Add it to
`docs/book/esh/50.automation-recipes.md`. Explain what a reader needs to
provide and what the script produces, then add a focused assertion to the
documentation example tests when the script can run without external services.

The existing examples in `crates/esh/tests/documentation_examples_tests.rs`
are a good pattern: they compile public ESH snippets and check the result of a
JSON data example. A complete contribution includes the recipe, a short
explanation of when to use it, and a regression check for its behavior.

## Cover an ESH edge case

Choose an ESH behavior or built-in edge case that affects a script you use.
Add a focused regression case beside the owning tests in `crates/esh/tests/`,
then update the language or built-in reference if the behavior is part of the
public contract. Prefer fixtures that use ESH's own built-ins and work across
operating systems.

The [development guide](/contributing/development#platform-support) explains
which platforms Everyinit supports and how to interpret exploratory platform
probes. A good contribution leaves the behavior and its limits clear in both
the test and the documentation.

## Improve a `.flow` editor interaction

Pick one editor interaction that would make authoring workflows easier, such
as a completion, diagnostic, or hover that is missing useful context. Trace
the behavior through `crates/evin-lsp/` and `editors/vscode/`, then add a
focused regression case and the smallest user-facing improvement that solves
the problem.

The [VS Code extension guide](/contributing/vscode-extension) describes how to
build and exercise the client. For a strong contribution, show the `.flow`
input, the current result, and the result a user should see after the change.

## Choose a starting point

Pick an opportunity that matches a problem you have encountered. Open an issue
to describe the change you have in mind, then follow the
[development workflow](/contributing/development) to find the owning module
and relevant checks. Keep your first pull request focused so it is easier to
review.
