# Release infrastructure

This page is for maintainers who operate release automation. Most contributors
do not need release credentials or to run these procedures. Changes to the
workflow itself belong in `.github/workflows/release.yml` and the release task
definitions under `.evin/release/`.

## Release flow

The **Release** workflow starts after successful CI on `main`. It checks the
exact commit's CI result, reconciles merged release proposals, and maintains
one open `automation/release` pull request. Review that proposal as an ordinary
pull request; it updates coordinated versions, changelog, lockfiles, and
generated catalogs.

When the proposal is merged, successful CI on the resulting main commit lets
Release build and verify Evin and ESH packages, create a tag on the merge
commit, and publish the release. It also publishes the VS Code extension and
`everyinit` npm package, and updates the signed Linux artifact mirror. GitHub
Releases, the Visual Studio Marketplace, npm registries, and the Cloudflare R2
mirror have separate publication steps.

The active `main` ruleset requires the **Dependency audit** check for pull
requests. Release publication has an additional exact-SHA gate: the latest
main **push** CI run for that commit must pass `Linux validation (quality,
tests, E2E, distribution)` and `CI gate`. A successful pull request check or a
run for another commit does not satisfy that release gate.

## Configure publisher credentials

The GitHub `release` environment needs these secrets:

| Secret | Purpose |
| --- | --- |
| `RELEASE_BOT_TOKEN` | Push the release proposal branch, create or update its pull request, inspect Actions runs, and create release tags. |
| `EVERYINIT_RELEASE_SIGNING_KEY` | Sign and verify artifact manifests for GitHub Releases and the R2 mirror. `RELEASE_SIGNING_KEY` remains a fallback name. |
| `CLOUDFLARE_ACCOUNT_ID` | Select the account that owns the artifact bucket. |
| `CLOUDFLARE_API_TOKEN` | Publish immutable artifacts and channel pointers to R2. |

The bot needs repository contents read/write, pull requests read/write, and
Actions read access. It must be able to update `automation/release` and create
release tags. The `GITHUB_TOKEN` does not create the release PR because that
would not trigger the normal pull request checks. Keep bot and signing
credentials in GitHub's environment secrets, never in the repository.

The `everyinit` package on npmjs uses GitHub Actions trusted publishing. In
the package's npm settings, authorize `dukasn/everyinit`, workflow
`release.yml`, and environment `release` to publish. No npm token is needed;
GitHub Packages uses the workflow token.

Marketplace publishing uses GitHub Actions OIDC trusted publishing. The
publisher is `everyinit`; the Marketplace configuration is tied to this
repository and `release.yml`. Do not add a Marketplace PAT unless trusted
publishing is intentionally replaced.

## Retry a failed release

Inspect the failing step and the release state before retrying. If the main
push CI succeeded but Release did not complete, dispatch **Release** with the
full main commit SHA. The workflow verifies the SHA and the merged release
proposal before publishing. Do not dispatch with a PR head or an unrelated
commit.

An existing tag must be annotated and point to the merge commit. A partial or
draft release may need repair or removal before retrying. Never move a published
tag. A completed release with its expected assets is safe to retry and becomes
a no-op.

If npm publishing reports that the package was not found or asks for a login,
check the package's trusted publisher settings on npmjs. The package may still
exist; those errors can mean npm no longer recognizes the release workflow as
an authorized publisher.
Correct the settings, then retry the failed Release run for the same version.

## Test the mirror locally

The local mirror workflow needs verified Linux archives and the private key
that matches `infra/get/release-key.pub`. Keep that key outside the repository.
Set the release inputs and seed Wrangler's local R2 storage:

```sh
export RELEASE_VERSION="$(grep -m1 '^  version:' .evin/workspace.flow | cut -d '"' -f 2)"
export RELEASE_CHANNEL=canary
export RELEASE_TARGET=x86_64-unknown-linux-musl
export RELEASE_BASE_URL=http://localhost:8787
export RELEASE_COMMIT="$(git rev-parse HEAD)"
export RELEASE_SIGNING_KEY_FILE="$HOME/.config/everyinit/release-key.pem"
cargo evin-dev run infra:mirror:seed
```

Run the local mirror Worker in one terminal and request its channel manifest in
another:

```sh
cargo evin-dev run infra:dev:mirror
```

```sh
curl -i http://localhost:8787/canary.json
```

For installer tests, run `cargo evin-dev run infra:dev:installer`; the local
installer Worker listens on port 8789. Local Workers use Wrangler's local
storage and do not publish artifacts. The installer verifies the manifest
signature before checking or extracting an archive. Do not change the signing
key without updating the pinned public key and installer configuration.

## Verify published files

Release checksum manifests use Ed25519. Download `SHA256SUMS`,
`SHA256SUMS.sig`, and the matching public key, then verify the signature and
checksums:

```sh
openssl pkeyutl -verify -pubin -inkey release-key.pub -rawin \
  -in SHA256SUMS -sigfile SHA256SUMS.sig
sha256sum -c SHA256SUMS
```

The public key is pinned at `infra/get/release-key.pub`. Distribution targets
and recovery behavior are implemented in the release workflow; update this
page when those procedures or credentials change.
