# Data, files, and HTTP

Most automation is moving information between a project, its files, and its services. ESH includes the common building blocks in its runtime, so a script can stay focused on the workflow instead of checking which host utilities exist.

## Read project data

`json` and `yaml` read either an inline document or a file. The `-g` (`--get`) option follows a dot path and writes the value to standard output, making it natural to use in command substitution.

```esh
VERSION="$(json -g version package.json)"
SERVICE_PORT="$(yaml -g service.port config.yaml)"

echo "Preparing $VERSION on port $SERVICE_PORT"
```

Validate input before continuing when a missing or malformed document should stop the workflow:

```esh
json -v package.json || exit 1
yaml -v config.yaml || exit 1
```

## Work with files explicitly

Wildcard characters are literal in ESH. Use `glob` when you want expansion, and `path` when a script needs to inspect a path instead of guessing from its spelling.

```esh
mkdir -p ./dist

for FILE in $(glob "./assets/*.svg"); do
  cp "$FILE" ./dist
done

path --exists ./dist || exit 1
archive ./dist/release.zip ./dist
sha256sum ./dist/release.zip > ./dist/release.zip.sha256
```

The [Runtime Reference](/reference/esh/runtime-reference) lists filesystem, archive, hash, and text commands with their options and exit statuses.

## Call a service without curl

`http` makes an in-process HTTP request. It succeeds for a 2xx response and returns a non-zero status for network errors or HTTP error statuses, so it composes with the same control flow as every command.

```esh
wait_port 127.0.0.1:8080 15s || exit 1

retry -n 3 -d 1s http GET http://127.0.0.1:8080/health || {
  echo "Service did not become healthy" >&2
  exit 1
}
```
