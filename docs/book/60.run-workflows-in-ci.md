# Run workflows in CI

The task graph you run locally can also be selected from CI. Keep task
definitions in `.evin/workspace.flow`; let the CI workflow prepare the runner
and invoke Evin.

## Invoke a target

For example, a GitHub Actions job can call the same target a developer runs:

```yaml
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      # Install Evin and the project toolchains required by the tasks.
      - name: Verify the repository
        run: evin run verify --verbose
```

The comment marks a real prerequisite: the runner must have Evin and the
commands used by the selected tasks installed and configured. Setup depends on
your release source, language toolchain, credentials, and CI provider, so it
belongs with that provider's runner configuration.

## Keep the responsibilities clear

- Evin resolves the target, its dependencies, environment, and built-in
  actions.
- CI prepares the operating system, installs Evin and project tools, provides
  secrets, and handles provider-specific status or artifact publishing.
- A task can still invoke commands with host-specific requirements. Reusing
  the graph does not make those commands available on every runner.

Prefer one CI invocation of a meaningful Evin target over duplicating each
task command in workflow YAML. Keep provider-specific setup and credentials in
the workflow. See [CI and platform support](/contributing/development#platform-support)
for Evin's current tested scope.

This repository follows the same boundary: its CI workflow prepares Linux
runners and invokes canonical tasks through `cargo evin-dev`. The root
[CI policy](https://github.com/dukasn/everyinit/blob/main/CI.md) explains why
the project currently focuses CI on Linux.
