# Pipelines and hooks

`evin run <TARGET>` accepts three kinds of target. All three resolve to task
names and then use the same dependency engine.

| Target | Example | Selection rule |
| --- | --- | --- |
| Task | `evin run test` | The exact task plus its transitive `needs` |
| Stage | `evin run Check` | Every task whose `stage` is exactly `Check`, plus prerequisites |
| Git hook | `evin run pre-commit` | Every task listing that hook in `on.hooks`, plus prerequisites |

Pass arguments intended for the hook after `--`. Git's generated hook shims do
this automatically:

```esh
evin run commit-msg -- .git/COMMIT_EDITMSG
```

## Bind tasks to hooks

```yaml
tasks:
  format:
    stage: Check
    description: "Check formatting before commit"
    on:
      hooks: [pre-commit]
    run: cargo fmt -- --check

  test:
    stage: Test
    description: "Run tests before push"
    needs: [format]
    on:
      hooks: [pre-push]
    run: cargo test --workspace
```

One task can list multiple hooks. A prerequisite does not need to repeat the
hook binding; graph resolution includes it through `needs`.

## Install the Git shims

```esh
evin sync
```

EVIN installs or updates the supported `pre-commit`, `commit-msg`, and
`pre-push` shims under `.git/hooks/`. Each shim changes to the repository root
and invokes `evin run <hook-name> -- <git-arguments>`.

> [!TIP]
> Run `evin sync --dry-run --verbose` to inspect planned hook content and
> built-in action resources without writing them.

By default, a shim executes the `evin` binary found on `PATH`. A repository
that develops EVIN or a source wrapper can opt into a different runner:

```yaml
workspace:
  name: evin-development
  version: "1.0.0-canary.100"
  install_hint: "cargo install --locked --path crates/evin"
  hook_runner:
    command: cargo
    args: [evin-dev]
```

`command` and every `args` item are passed as separately quoted arguments. The
runner executes from the repository root before receiving
`run <hook-name> -- <git-arguments>`.

## Separate task checks from Git policy

A hook invocation has two layers:

1. EVIN applies the supported policy checks from the file referenced by
   `workspace.rules`.
2. If policy succeeds, EVIN runs the tasks bound to that hook.

| Hook | Built-in policy responsibility |
| --- | --- |
| `pre-commit` | Staged-file rules, LFS/submodule restrictions, authorship checks, and empty-commit policy |
| `commit-msg` | Commit-message format/fields and configured history integrity checks |
| `pre-push` | Branch/tag naming, tag deletion and annotation rules, remote restrictions, and force-push policy |

An unhandled custom hook can still select tasks, but it does not gain one of
these policy implementations automatically.

> [!CAUTION]
> `commit-msg` needs the path Git passes to the commit message file. Manual
> testing without `-- <path>` correctly fails because the policy engine has no
> message to validate.

## Use the same target in CI

After the local hook is useful, CI should invoke the workflow target rather
than duplicate its commands:

```yaml
- name: Run repository checks
  run: evin run pre-commit --verbose
```

That keeps graph selection, environment construction, action validation, and
failure behavior in one repository-owned definition.

The complete policy schema is in
[Git rules configuration](/reference/git-rules-configuration).
