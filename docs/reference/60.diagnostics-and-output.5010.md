# Diagnostics and output

> **RFC-5010 · Implemented Interface**
> Source crates: `evin-diagnostic`, `evin-ui`, and `evin-action-sdk`

EVIN diagnostics are structured inside the process and rendered for a human
terminal. The CLI does not currently expose a JSON or JSON Lines diagnostic
mode.

## Diagnostic model

| Field | Type | Meaning |
| --- | --- | --- |
| `title` | string | Short localized or action-provided heading |
| `code` | locale key plus named string arguments | Stable lookup identity or custom runtime message |
| `severity` | `Error`, `Warning`, or `Info` | Rendering class; default is `Error` |
| `hint` | optional string | Suggested correction |
| `location` | optional path or byte span | Source file context used by the snippet renderer |

A location is either a path with optional line/column values or a byte offset
and length with an optional label. When source text is available, the UI maps
the location to a cropped code frame.

```text
× Error [issue-invalid-stage] Invalid task stage
│
│  .evin/workspace.flow
│  ...source context...
│
◇ hint: choose one of the declared stages
```

The exact wording and symbols vary with locale, terminal width, and color
support.

`evin check` embeds these structured diagnostics inside its `Workspace › Check`
frame. Each affected manifest is marked with `×`, followed immediately by its
fenced configuration findings. Configuration and template locations produce
source snippets; dependency graph errors use the same diagnostic fence but may
omit a snippet when the resolved graph does not retain an exact source span.
Selector mistakes use the compact discovery failure format because they do not
originate in a manifest.

Normal execution applies the same native-action contract to the selected target
graph during configuration resolution. A malformed `with:` payload therefore
fails **Resolving configuration** before task execution begins.

## Pipeline presentation modes

| Mode | Enable with | Additional information |
| --- | --- | --- |
| Normal | default | Phase/task progress and failures |
| Verbose | `--verbose` | Captured output from successful tasks and detailed sync/init resources |
| Debug | `--debug` or `EVIN_LOG=debug` | Workspace discovery, DAG edges, non-root task working directories, environment keys, subprocess start/finish, durations, and footer flags |
| Dry run | `--dry-run` | Planned shell/action operations and uncertainty from skipped work |

Debug records are rendered as human-readable pipeline entries such as
`[E_601] command=...`; they are not a stable machine serialization contract.

## Task output and failures

ESH command output is captured and forwarded into the pipeline reporter. EVIN
keeps stdout and stderr as distinct stream labels internally, redacts known
secret values, and can show command output when a task fails or verbose mode is
enabled.

A non-zero ESH or external-command status fails the task. Dependents are not
started, and EVIN exits non-zero. Cancellation produces an aborted workflow and
requests tree-wide process cleanup.

## Redaction boundary

EVIN loads redactable values from `.env`, common secret-like host variable
names, and variables marked `type: secret` in
`.evin/environment.flow`. Known values at least four characters long are
replaced with `***` in captured output.

> [!WARNING]
> Diagnostics can still reveal non-secret paths, task names, command text, and
> environment key names. Debug output lists injected keys but should never be
> treated as an appropriate place to print credential values.
