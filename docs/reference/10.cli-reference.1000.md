# CLI reference

> **RFC-1000 · Implemented Interface**
> Scope: `crates/evin/src/main.rs` · Command parser: Clap

The `evin` executable initializes repository configuration, synchronizes Git
integration, and runs declared workflow targets.

## Synopsis

```text
evin [OPTIONS] <COMMAND>

Commands:
  init
  sync
  list
  explain
  check
  lsp
  run
  help
```

Global options may be written with a subcommand:

| Option | Effect |
| --- | --- |
| `-v`, `--verbose` | Retain successful task output and show additional sync/init details |
| `--dry-run` | Select planning mode for workflow commands and built-in actions |
| `--debug` | Show configuration, graph, environment, process, and timing records |
| `-h`, `--help` | Print help for the current command |
| `-V`, `--version` | Print the package version |

> [!NOTE]
> `--dry-run` is most useful with `run` and `sync`. `init` is itself a file
> creation command and currently performs initialization when selected.

## `evin init`

```text
evin init [OPTIONS] [PATH]
```

| Option | Short | Generated file |
| --- | --- | --- |
| `--workspace` | `-w` | `<PATH>/.evin/workspace.flow` |
| `--policy` | `-p` | `<PATH>/.evin/policy.json` |
| `--env` | `-e` | `<PATH>/.evin/environment.json` |
| `--module <MODULE>` | `-m` | `<PATH>/<MODULE>/.evin/module.flow` |
| `--all` | `-a` | Workspace, repository policy, and environment files |

With no selection flag, `init` creates only the workspace manifest. `PATH`
defaults to the current directory and is created when missing. Existing
configuration files are skipped, not overwritten.

```esh
evin init --all services/api
evin init --module crates/core
```

## `evin sync`

```text
evin sync
```

`sync` loads the workspace, validates built-in action configuration, plans the
resources required by those actions, and installs or updates Git hook shims.
The supported policy hooks are `pre-commit`, `commit-msg`, and `pre-push`.

```esh
evin sync --dry-run --verbose
```

In dry-run mode, the command reports planned changes without applying hook
plans.

As its first synchronization phase, `sync` checks for an unresolved
`.evin/release-lock.json`. When that lock is the only unresolved path, EVIN
reads Git's base, ours, and theirs stages, fingerprints the final merged index,
reuses matching state, and assigns the next revision only for a genuinely new
merged fingerprint. Both sides must agree on the semantic version and tag.
Normal mode writes and stages the reconciled lock; `--dry-run` displays the
proposed JSON without staging it. When the lock is not conflicted, the phase is
a no-op.

For a conflict, resolve all non-lock paths first, run `evin sync`, inspect the
staged lock and synchronized resources, continue the Git operation, then run
`evin check`.

## `evin list`

```text
evin list
```

Lists the loaded workspace version, every root and module-qualified task,
using EVIN's standard framed terminal presentation. Tasks are grouped by their
workspace or module manifest and each heading links to the manifest's absolute
`file://` path. Entries show the qualified task name and configured description
without exposing implementation steps. The final catalog summary reports task
counts for stages, hooks, and modules. Groups and entries are sorted
deterministically.

## `evin explain`

```text
evin explain <TARGET>
```

Resolves a task, stage, or hook through the same registry used by `run`, then
prints a compact dependency-first execution plan. Exact tasks include their
stage, effective working directory, direct dependencies, required environment
variable names, and summarized steps. Stages and hooks show their resolved task
count. Environment values and action inputs are intentionally omitted.

In an interactive terminal, discovery presentation is styled and written to
stderr like the rest of EVIN's UI. When stdout is redirected, the same Unicode
layout is written there with ANSI styling removed.

## `evin check`

```text
evin check [OPTIONS] [TARGET]
```

| Option | Short | Effect |
| --- | --- | --- |
| `--workspace` | `-w` | Validate only root workspace tasks and root configuration manifests |
| `--module <MODULE>` | `-m` | Validate only tasks declared within the specified module or namespace |
| `[TARGET]` | | Validate a specific task, stage, or hook and its complete prerequisite graph |

The workspace, module, and target selectors are mutually exclusive. `check`
performs zero-execution static analysis across the repository's workflow
contracts:

- Validates that all `.evin/workspace.flow`, `.evin/module.flow`, included namespace files, `.evin/policy.json`, and `.evin/environment.json` manifests parse without schema or syntax errors.
- Resolves all declared task dependencies (`needs:`) to ensure no missing prerequisites exist.
- Performs full topological sort across the selected task graph to guarantee zero circular dependency cycles.
- Resolves every native `uses:` identifier and validates its complete `with:` contract, including unknown options, missing fields, invalid types, and action-specific constraints.
- Verifies action step `${...}` template expression syntax and reports malformed expressions as errors.

```esh
evin check                      # Statically validate entire repository
evin check --workspace          # Validate only root workspace tasks
evin check --module release     # Validate release module / namespace tasks
evin check release:bump         # Validate specific target and its prerequisites
```

The command never executes tasks, actions, hooks, or shell steps. It validates
every selected action step and reports at most one configuration error per step
in a single pass. Affected manifests are marked with `×`, and their fenced
diagnostics appear directly beneath them with cropped source snippets whenever
a location is available. DAG errors remain actionable through task names and
cycle paths even when no exact source span is available. Warnings are displayed
but exit successfully; errors and invalid selectors exit with status `1`.

Interactive output is styled on stderr. Redirected successful reports are
written to stdout without ANSI styling, while redirected failures remain on
stderr.

## `evin lsp`

```text
evin lsp
```

Starts a single-workspace Language Server Protocol server over standard input
and output. It resolves the workspace from `initialize.rootUri`, falling back
to the process working directory when no root URI is supplied; non-file root
URIs are rejected. Standard output is reserved exclusively for framed JSON-RPC
messages and startup or runtime failures are written to standard error.

The server uses full-document synchronization and rebuilds its overlay-aware
configuration snapshot after each open, change, or close. Analysis is
debounced and runs in the background so document edits do not block JSON-RPC
requests. It provides push diagnostics, completion, hover, CodeLens, document
and workspace symbols, definitions, and references for workspace, module,
namespace, Flow RepositoryPolicy, and `.evin/environment.json` documents. It supports
single-workspace task execution through `workspace/executeCommand`; the server
relays versioned `evin/pipelineEvent` notifications and standard work-done
progress, and accepts `$/cancelRequest` for active task runs. Task output is
opt-in. Task execution uses the normal Evin runner and does not expose Git
inspection or artifact publication as LSP operations. Multi-root workspaces
are not supported. Snippet completions are emitted only when the client
advertises snippet support during initialization.

An empty completion response means Evin has no suggestions for that cursor.
Editors can still show suggestions from their own word-based or third-party
providers. In VS Code, disable word-based suggestions for the language ID
configured for the Evin LSP client when you want an empty result to leave the
completion list empty. The repository's generic VS Code LSP client uses
`plaintext`:

```json
{
  "[plaintext]": {
    "editor.wordBasedSuggestions": "off"
  }
}
```

An editor client can also use a first-line `#!evin/v1` comment to identify
an Evin document outside `.evin/`; that marker does not add an unregistered
file to the workspace configuration graph.

## `evin run`

```text
evin run [OPTIONS] <TARGET> [-- <ARGS>...]
```

| Run option | Effect |
| --- | --- |
| `--parallel` | Force ready tasks to use parallel execution for this invocation |
| `--sequential` | Force ready tasks to use linear execution for this invocation |
| `--events ndjson` | Write versioned pipeline events as newline-delimited JSON to stdout |
| `--events-output` | Include captured task stdout and stderr in the NDJSON stream; requires `--events ndjson` |
| `-- <ARGS>...` | Route declared value-less action flags such as `--host` to their owning native action; preserve non-flag values as Git-hook payload |

`--parallel` and `--sequential` conflict. Without either flag, EVIN uses
`workspace.execution`, falling back to `linear`.

When `--events ndjson` is enabled, stdout contains one versioned JSON event per
line, and the interactive pipeline UI continues to render on stderr. Captured
task output is omitted unless `--events-output` is also supplied. Output uses a
bounded queue; if it overflows, an `output_dropped` event reports the number of
omitted lines. Lifecycle events remain lossless while the stream consumer is
attached.

Each event has `schema_version`, `run_id`, `seq`, `timestamp`, `kind`, and
`payload` fields. `seq` starts at 1 and increases for each delivered event in a
run; dropped task output is reported by `output_dropped`. Timestamps use RFC
3339 UTC. Consumers should ignore unknown event kinds and payload fields.
Adding event kinds or optional fields is compatible; renaming/removing event
kinds, removing required fields, or changing field types requires a schema
version increment.

Trailing flags must be declared by exactly one native action in the selected
task graph. Unknown flags and duplicate declarations fail during configuration
resolution before any task runs. An action with no declared flags rejects
trailing flags rather than passing them to unrelated actions.

After resolving the requested target and its dependencies, EVIN statically
validates every native action in that selected graph. Invalid `uses:` references
or `with:` payloads fail the **Resolving configuration** phase before any shell
step or action starts. Invalid tasks outside the selected graph do not block the
run; use `evin check` to validate the complete workspace.

### Target resolution

| Input shape | Context | Resolution |
| --- | --- | --- |
| Exact task ID, such as `test` or `docs:build` | Task | Selected task and transitive prerequisites |
| Declared Pascal-style stage, such as `Check` | Stage | Every task assigned to that stage and their prerequisites |
| Known or declared hook, such as `pre-commit` | Hook | Every task bound through `on.hooks` and their prerequisites |

Unknown lowercase task targets and unknown stages produce a diagnostic and may
include a nearest-name suggestion.

```esh
evin run docs:build
evin run Check --parallel
evin run commit-msg -- .git/COMMIT_EDITMSG
```

### Runtime and cancellation

`run` commands execute through ESH. EVIN captures their output for the pipeline
UI, records the external command status in debug mode, and treats a non-zero
status as task failure. `Ctrl+C` cancels the active graph; supervised external
process trees are cleaned up by the shared process layer before the UI exits.

### Exit status

Successful invocations exit with status `0`. CLI parsing errors and failed or
cancelled workflows exit non-zero. The current CLI does not promise to forward
an arbitrary failed child status as EVIN's own process status.

> [!TIP]
> Treat `evin --help`, `evin list`, `evin explain --help`, and `evin run --help` as the compact
> executable contract; this page supplies the behavioral context around it.
