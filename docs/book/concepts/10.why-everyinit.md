# Why Everyinit

Most repositories outgrow a single list of commands. What starts as three lines
in a `README` splits across package manifests, shell scripts, local Git hook
shims, `.env.example` notes, and CI workflow YAML. Each surface solves a real
problem on its own, yet none of them share a common model of task dependencies,
inputs, or repository rules.

Everyinit gives that surrounding work an explicit, inspectable structure without
replacing the build tools, test runners, or compilers a project already trusts.

## The problem with repository glue

When project automation grows organically, four distinct concerns usually get
mixed together:

- **Task orchestration** hides inside ad-hoc scripts that call other scripts,
  making prerequisites and execution order hard to see before a command runs.
- **Environment expectations** live in prose or one developer's shell profile,
  so tasks fail late when a required variable is missing or malformed in CI.
- **Repository conventions**—commit formats, branch naming, and release bump
  rules—drift between local hook tools and release scripts.
- **Procedural logic** gets crammed into quoted YAML strings or brittle POSIX
  one-liners that are difficult to test, lint, or clean up on failure.

Fixing that drift does not require inventing a monolithic build language. It
requires giving each responsibility its own clear contract.

## Four responsibilities, kept distinct

Everyinit separates repository automation into four focused files. Only
`.evin/workspace.flow` is required to start; the remaining contracts are
optional layers you add when a repository needs them.

| Layer | File | Status | Responsibility |
| --- | --- | --- | --- |
| 01 · Workflow | `.evin/workspace.flow` | Required | Declares stages, tasks, `needs` dependencies, module boundaries, and Git hook bindings. |
| 02 · Environment | `.evin/environment.json` | Optional | Defines typed variable schemas, defaults, presets, injection scopes, and secret redaction. |
| 03 · Policy | `.evin/policy.json` | Optional | Captures commit formats, branch rules, staged-file checks, and SemVer release mappings. |
| 04 · Script | `*.esh` | Optional | Expresses branching, structured data handling, HTTP/file work, and cleanup outside YAML strings. |

Keeping these boundaries separate has practical consequences:

- Static analysis stays side-effect-free. `evin check` and `evin lsp` validate
  task graphs, action schemas, environment references, and policy rules without
  executing shell code.
- Editors can offer accurate completion, hover documentation, and diagnostics
  for `.flow`, `environment.json`, `policy.json`, and `.esh` through standard
  JSON Schemas and Language Server Protocol servers.
- Reviewers can see whether a pull request changes task wiring, environment
  inputs, repository governance, or script logic from the file path alone.

## Adopt one task at a time

Adopting Everyinit does not require rewriting existing build scripts or moving
everything at once:

1. Run `evin init` to create `.evin/workspace.flow` and point one or two tasks
   at commands your repository already runs (`cargo test`, `npm run lint`,
   `pytest`).
2. Inspect how the graph resolves with `evin explain` and `evin run --dry-run`
   before wiring tasks into hooks or CI.
3. Add `.evin/environment.json`, `.evin/policy.json`, child `module.flow`
   files, or `.esh` scripts only where plain commands stop being clear enough.

Tasks that wrap existing project commands stay trivial to unwind later; custom
`.esh` scripts or built-in `evin/*@v1` delivery steps take proportional effort
to rewrite if you migrate away. See
[removing Everyinit](/book/installation#removing-everyinit).

## Compared with other tools

Everyinit overlaps intentionally with parts of familiar developer tools while
drawing a different boundary around the repository as a whole.

### `mise`

`mise` excels at pinning and installing language toolchains (`rust`, `node`,
`python`), managing per-directory environment variables, and running lightweight
project tasks. Everyinit does **not** download or manage language toolchains—in
fact, Everyinit's own repository uses `mise` to select pinned Rust and Node
versions while using Evin to run its workspace graph, hooks, and release
pipelines.

If a repository primarily needs reproducible tool versions plus a handful of
task shortcuts, `mise` alone is often enough. Add Everyinit alongside `mise`
when you want static validation across multi-module task graphs, scoped
environment schemas with `secret` stream redaction (`pure: true` / `presets`),
enforced commit and release policies (`.evin/policy.json`), dedicated LSP
tooling, ESH scripting, or native packaging and release actions.

### `Task` (`Taskfile.yml`)

`Task` provides declarative YAML task orchestration with dependencies, status
checks, and cross-platform shell execution. Where `Task` embeds shell fragments
and Go templates directly inside `Taskfile.yml`, Everyinit splits orchestration
(`.flow`), typed environment validation (`environment.json`), repository
governance (`policy.json`), and procedural scripts (`*.esh`) into distinct
contracts backed by dedicated language servers and zero-execution `evin check`
diagnostics. `Task` is a mature choice when you need macOS and Windows binaries
today; Everyinit fits Linux workflows that benefit from stricter static
contracts and integrated repository policy and release actions.

### `just` and `Make`

`just` is a clean command runner for short repository recipes, and `Make` excels
at file-timestamp build rules. Neither models typed environment schemas with
secret redaction, native Git hook and commit/release policy contracts, scoped
Chrome/Perfetto execution traces, or statically validated delivery actions.
Choose `just` when you only want a flat menu of terminal commands; choose
Everyinit when tasks, hooks, environment contracts, and CI targets need to share
one validated graph.

### `npm`, `Cargo`, and language task scripts

Package-manager scripts know their own language toolchain well and remain the
right place for single-tool commands (`cargo clippy`, `npm test`). They break
down in polyglot repositories or when workflows span documentation generation,
Git policies, archive packaging, and cross-directory dependencies. Evin
orchestrates those existing package commands rather than replacing them.

### `lefthook`, `Husky`, and `pre-commit`

Dedicated hook managers focus on wiring Git events to commands. In Everyinit, a
hook binding (`on.hooks: [pre-commit]`) points to a regular task in the
workspace graph, while `.evin/policy.json` handles commit-message, branch, and
staged-file rules natively. You can inspect hook targets ahead of time with
`evin explain pre-commit` and reuse those same task definitions in CI, subject
to the runner's installed tools, environment, and operating system.

### CI workflow YAML

GitHub Actions, GitLab CI, and similar platforms own runner provisioning,
cloud credentials, matrix scheduling, and remote status checks. Keeping task
definitions in `.evin/workspace.flow` lets developers inspect and run the same
`evin run verify` target locally before pushing, leaving CI YAML thin and
focused on runner setup and secrets.

## When not to use Everyinit

Everyinit is not the right fit for every problem:

- **Hermetic or containerized build sandboxing:** Evin is a workflow
  orchestrator and process-group supervisor, not a hermetic or containerized
  build system like Bazel, Nix, or Earthly. See the
  [execution and trust model](/book/concepts/execution-and-trust-model) for
  exact process boundaries.
- **Cross-platform CLI teams today:** Official prebuilt binaries and required CI
  currently target **Linux x86_64** while core contracts mature in canary
  development.
- **Distributed job or infrastructure engines:** Evin coordinates local
  processes within one workspace, not remote worker clusters or cloud
  infrastructure provisioning (such as Terraform or Pulumi).
