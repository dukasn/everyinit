# Namespace configuration

> **RFC-4515 · Implemented Interface**
> Source types: `NamespaceYaml` and `NamespaceConfig`

A namespace file organizes logical workflow tasks (such as release routines,
database migrations, or maintenance checks) into a dedicated YAML document
without requiring a separate physical codebase directory or submodule.

Namespace files are loaded when registered in `workspace.include`.

## Schema

```yaml
namespace:
  name: release
  description: "Release engineering and distribution pipelines"

env:
  RELEASE_CHANNEL: canary

values:
  archive_prefix: evin
  staging_dir: "dist/release-stage"

tasks:
  clean:
    stage: Publish
    description: "Require a clean working tree"
    steps:
      - run: cargo run --locked -p esh -- scripts/release/preflight.esh

  bump:
    stage: Publish
    description: "Calculate and apply the next canary version"
    needs:
      - release:clean
      - verify
    steps:
      - uses: evin/version-bumper@v1
        with:
          initial_version: "1.0.0-canary.100"
          channel: canary
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `namespace.name` | string | yes | Namespace prepended to every task in this file (e.g. `release:clean`) |
| `namespace.description` | string | no | Human-readable UI and catalog summary shown in `evin list` |
| `env` | string map | no | Environment variables inherited by all tasks in this namespace |
| `values` | string map | no | Document-level action-template values available to tasks in this namespace |
| `tasks` | task map | no | Map of task declarations using the standard task schema |

Unknown fields are rejected.

## Inclusion in `workspace.yaml` and `module.yaml`

Namespace files can be included by both the root workspace and individual modules using either list or map format:

### In `workspace.yaml`
```yaml
workspace:
  name: main
  version: "1.0.0"
  include:
    - .evin/release.yaml
    - .evin/maintenance.yaml
    - .evin/packages.yaml
```

Alternatively, use a map to assign or override the namespace prefix explicitly:

```yaml
workspace:
  name: main
  version: "1.0.0"
  include:
    release: .evin/release.yaml
    ops: .evin/maintenance.yaml
```

### In `module.yaml`
```yaml
module:
  name: api
  include:
    - .evin/routes.yaml
    - .evin/db.yaml
```

Paths in `module.include` resolve relative to the module directory. If the namespace name matches the module name (e.g. `api`), tasks are prefixed as `api:<task>`. If a distinct sub-namespace is used (e.g. `routes`), tasks are prefixed as `api:routes:<task>`.

The alias `includes` is also accepted.

For distro packages, register a normal namespace file such as
`.evin/packages.yaml`; it contains shared `values` and standard
`evin/archive@v1` tasks with inline `with.package` objects. It is not a
separately discovered metadata file. See the Archive action reference for the
package schema and per-format examples.

## Task names and dependencies

Tasks defined inside a namespace file are named `<namespace>:<task>` (or `<module>:<namespace>:<task>` when included by a module). For example, `clean` in `release.yaml` becomes `release:clean`.

When declaring dependencies in `needs`, always use the fully qualified task name:

```yaml
tasks:
  verify:
    stage: Publish
    needs:
      - release:clean   # Prerequisite in the same namespace
      - verify          # Prerequisite at the workspace root
    steps:
      - run: cargo check --workspace --locked
```

Explicit task referencing ensures:
* **Zero ambiguity**: There is never any conflict between a root task (`verify`) and a namespace task (`release:verify`).
* **Global searchability**: You can search the codebase for `release:clean` to find every prerequisite edge and invocation.

## Execution context and precedence

* **Workspace inclusion**: Tasks declared in namespace files included by `workspace.yaml` run from the **workspace root** by default.
* **Module inclusion**: Tasks declared in namespace files included by a `module.yaml` run from that **module directory** by default.

A task may always supply its own `cwd` to override the default.

Template values and environment variable pools resolve with the following precedence:

| Inclusion source | Value precedence (low → high) | Environment precedence (low → high) |
| --- | --- | --- |
| `workspace.include` | workspace `values` → namespace `values` → task `values` | root `.env`/workspace `env` → namespace `env` → task `env` |
| `module.include` | workspace `values` → module `values` → namespace `values` → task `values` | root `.env`/workspace `env` → module `env` → namespace `env` → task `env` |

## When to use modules vs. namespaces

| Feature | Physical Modules (`module.yaml`) | Logical Namespaces (`namespace.yaml`) |
| --- | --- | --- |
| **Primary purpose** | Codebase packages and subprojects (e.g. `crates/api`, `apps/web`) | Workflow concerns (e.g. `release`, `maintenance`, `db`) |
| **Location** | `<directory>/.evin/module.yaml` beside source code | Arbitrary file (e.g. `.evin/release.yaml`) |
| **Registration** | `workspace.modules: [path/to/dir]` | `workspace.include` or `module.include` |
| **Default `cwd`** | The module directory (`crates/api`) | Workspace root (when in `workspace.yaml`) or module dir (when in `module.yaml`) |
