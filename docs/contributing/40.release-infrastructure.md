# Release infrastructure setup

Successful main push CI invokes **Release**, which maintains one
`automation/release` PR using Evin. The initial untagged workspace proposes
`v0.1.0`. Review and merge it by merge commit, squash, or rebase. For each
method GitHub records the resulting main commit as the merged PR's
[`merge_commit_sha`](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request).
Once that exact commit's main push CI succeeds, Release
checks that it is on main and belongs to the merged release PR, builds and
verifies Evin and ESH Linux musl archives, creates an annotated tag on that
commit, and publishes a GitHub Release. Identification uses the merged PR's
record, not the continued existence of its head branch. No unmerged proposal
commit is tagged, and an ordinary main push or a tag push cannot publish.

Configure a `RELEASE_BOT_TOKEN` secret for an app or bot with repository
**Contents: read and write**, **Pull requests: read and write**, and
**Actions: read** permissions. The bot must also be permitted to force-update
`automation/release` and create release tags. Both Git and the GitHub CLI use
this token, including for CI lookup and publication; the workflow grants no
permissions to the default `GITHUB_TOKEN` and does not rely on the repository
setting that allows Actions to create or approve pull requests.

The bot token is essential: a branch push or PR created with `GITHUB_TOKEN`
does not trigger normal PR CI. The workflow fails rather than silently
creating an untested PR if the secret is missing. Protect main and release
tags; do not allow untrusted users to modify the bot branch. Publishing
happens in the same run as the tag push and does not rely on a tag event
starting another workflow.

Configure `CI gate` as a required check. The Release workflow queries the
latest main **push** CI run for the exact SHA and requires both `Linux
validation (quality, tests, E2E, distribution)` and `CI gate` to succeed.
A successful PR run, dispatch run, older run, or different SHA is insufficient.
Runs are serialized; a stale main run skips proposal maintenance, leaving the
latest main CI run to reconcile it. Before proposing, the workflow checks
merged release PRs reachable from that main commit: each must have its
annotated tag at the merge SHA and a complete published release. An untagged
or partially published merge fails the run rather than opening a duplicate
proposal, including when a later main push finishes CI first. GitHub
concurrency may replace a pending run with a newer one. If a release merge run
was skipped or failed, manually run **Release** with the full merge SHA after
its main push CI succeeds; then retry the latest main SHA to maintain the PR.
If main advances while a proposal is being reconciled, the run closes any
open proposal and fails so the latest main run can recreate it safely.

The validation job disables incremental compilation and debug information in
its development and test builds to reduce hosted-runner disk usage. Its
separate host and musl caches exclude workspace build artifacts, so version
changes do not accumulate obsolete workspace binaries across releases.

A tag already present must be annotated and point at that exact merge SHA;
conflicts fail without overwriting it. A completed release with both expected
assets is a no-op on retry. A failed operation may leave a tag or draft/partial
release. Inspect the release and assets, then repair or remove the incomplete
release before retrying; the automation never silently overwrites it. Never
move an already published tag. Releases publish only to GitHub, not crates.io,
Cloudflare, or native package repositories.
