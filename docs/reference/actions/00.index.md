# Workflow Actions

Built-in actions place release engineering operations inside EVIN's task graph.
They use an exact `uses` identifier, receive configuration under `with`, run in
the task context, and publish named outputs to dependent tasks.

> [!IMPORTANT]
> These actions are compiled into the EVIN executable. The current
> implementation does not download action code from a registry and does not
> treat these identifiers as plugins.

## Action catalog

| Identifier | Primary input | Normal side effect | Published outputs |
| --- | --- | --- | --- |
| [`evin/docs@v1`](/reference/actions/documentation-action) | Markdown or reStructuredText, locale and version sources | Framework-neutral page data and route manifest | `manifest_path`, `page_count` |
| [`evin/catalog@v1`](/reference/actions/catalog-action) | Markdown or reStructuredText symbol and keyword entries | JSON tooling catalog | `output_file`, `symbol_count` |
| [`evin/archive@v1`](/reference/actions/archive-action) | Globs (`tar.gz`) or inline package payloads (`deb`/`apk`/`arch`) | Reproducible archive or native package artifact | `path`, normally `size` |
| [`evin/changelog@v1`](/reference/actions/changelog-action) | Git history and repository policy | Rewritten Markdown changelog | `path`; conditional `version`, `tag`, `notes_path` |
| [`evin/git-release@v1`](/reference/actions/git-release-action) | Git worktree or existing index | One commit, optional annotated tag, optional push | conditional `tag` |
| [`evin/version-bumper@v1`](/reference/actions/version-bumper-action) | Git history, repository policy, and configured files | File edits and optional commit and annotated tag | `version`, `changed`, normally `tag` |
| [`evin/review-request@v1`](/reference/actions/review-request-action) | Configured shell commands | Creates, updates, or closes one review request through those commands | `state`, conditional `id` |
| [`evin/release-sync@v1`](/reference/actions/release-sync-action) | Provider release state, Git history, and distribution artifacts | Offline reconciliation plan and file-backed notes | `plan`, `delta_count`, `reconciled` |

## Shared action-step contract

An action step has `uses` and may have `with`. The action's deserializer rejects
unknown configuration fields. Steps in one task execute in source order; a
failure stops the remaining steps and prevents dependent tasks from starting.

```flow
values:
  artifact_name: example

tasks:
  package:
    stage: Release
    steps:
      - uses: evin/archive@v1
        with:
          path: "dist/${artifact_name}.tar.gz"
          include: [LICENSE]

  inspect:
    stage: Release
    needs: [package]
    run: |
      echo "archive: ${package.path}"
      echo "bytes: ${package.size}"
```

Action strings are evaluated in the task's template context before execution.
The public forms are `${value}`, `${env.NAME}`, and `${task.output}`. A task
output is readable only from a resolved prerequisite, normally declared with
`needs`. A few actions also define local placeholders such as `${version}`;
their pages list those separately.

> [!NOTE]
> Relative filesystem inputs use the task `cwd` when the action goes through
> the action SDK filesystem. The documentation action performs its own source
> and output path resolution from the workspace root; its page records that
> difference.

## A composed release graph

The actions are independent operations. Composition is explicit in the graph,
which keeps calculation, generated files, packaging, and Git history visible as
separate failure boundaries.

```flow
tasks:
  bump:
    stage: Release
    steps:
      - uses: evin/version-bumper@v1
        with:
          files: [Cargo.toml]

  changelog:
    stage: Release
    needs: [bump]
    steps:
      - uses: evin/changelog@v1
        with:
          version: "${bump.version}"

  package:
    stage: Release
    needs: [bump, changelog]
    steps:
      - uses: evin/archive@v1
        with:
          path: "dist/project-${bump.version}.tar.gz"
          include: [target/release/project, CHANGELOG.md, LICENSE]
          prefix: "project-${bump.version}"
          layout: relative

  release:
    stage: Release
    needs: [bump, changelog, package]
    steps:
      - uses: evin/git-release@v1
        with:
          stage: all
          message: "chore(release): ${bump.version}"
          tag: "${bump.tag}"

  delivery:
    stage: Delivery
    needs: [release]
    steps:
      - uses: evin/release-sync@v1
        with:
          state: ".evin/actions/release-sync/remote-state.v1.json"
          plan_out: ".evin/actions/release-sync/plan.v1.json"
          artifacts_dir: "dist"
```

The example intentionally leaves Git mutation to the `release` action before
running `delivery` reconciliation. Enabling `git.commit` inside the version
bumper is an alternative; do not then add a Git release action unless a second
commit is intended.

## Dry-run behavior is action-specific

`evin --dry-run run <target>` selects dry-run providers, but each action decides
which work is virtualized. Do not assume every action is read-only merely because
the global flag is present.

| Action | Implemented dry-run behavior |
| --- | --- |
| Documentation | Parses and serializes the complete data package in a temporary directory, then removes it. |
| Archive | Resolves inputs but does not create the archive. It emits `path` and `size: "0"`; unresolved upstream inputs emit `size: unknown` and an unverified plan. |
| Changelog | Scans and formats Git history but does not write the changelog. It emits `path`, may emit release metadata, and marks generation unverified. |
| Git release | Uses virtual staging, commit, and tag operations. It still checks repository state, identity, and tag validity; a configured tag is published as an output. |
| Version bumper | Calculates from real Git history and plans file/Git changes. A planned Git commit emits `version` but returns before publishing `tag`, and marks the task unverified. Other no-commit paths normally publish both. |
| release sync | Ingests remote state, verifies Git tags, changelog, and artifacts, and evaluates the full plan. In dry-run mode, it calculates actions and emits outputs without writing note slices or plan files to disk. |

Use the action-specific output tables before consuming dry-run state. An output
that is conditional in normal execution remains conditional in a plan.
