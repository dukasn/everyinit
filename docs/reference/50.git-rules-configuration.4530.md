# Git rules configuration

> **RFC-4530 · Implemented Interface**
> Source types: `GitRulesRoot` and `RulesValidator`

The local file referenced by `workspace.rules` (typically `.evin/gitrules.flow`) defines repository-wide Git governance, conventional commit formatting, branch naming patterns, release impact rules, and security/safety policies enforced by generated Git hooks (`commit-msg`, `pre-commit`, `pre-push`).

Evin supports local rules paths; remote HTTP and HTTPS rule sources are rejected.

The Evin language server resolves GitRules fields through the same nested schema
shown below. Hovering a field such as `commits.message_format` shows its type and
purpose at the exact key; the containing catalog section supplies additional
examples. Completion offers fields for the current object and omits fields
already present. Keys under `commits.fields`, `releases.change_types`, and
`releases.packages` are user-defined names. The editor reports unknown or
duplicate fixed fields, wrong value types, missing required fields, and invalid
enum choices with source ranges. GitRules parsing and hook validation remain
authoritative when Evin runs.

## Root schema

````lsp
target: [GitRules]
language: flow
title: Git rules configuration
synopsis: "#!evin/v1\nversion: 1\nname: Git Development Standard\ndescription: Repository rules and release policy\n\ncommits: {}\nreleases: {}\nbranches: {}\ntags: {}\npull_requests: {}\nauthorship: {}\nhistory: {}\nfiles: {}\nlfs: {}\nsubmodules: {}\nremotes: {}"
summary: Define repository Git governance, conventional commit formats, release impact rules, and Git hook policies.
category: configuration
---
`.evin/gitrules.flow` governs Git policies outside workflow task execution.

It establishes repository standards for commit messages, branch names, release version bumps, changelog sections, staged content scanning, and push restrictions enforced by Evin's Git hooks (`commit-msg`, `pre-commit`, `pre-push`) and release actions.

### Root Namespaces

| Namespace | Primary Consumer | Purpose |
| --- | --- | --- |
| `version` | Parser validator | Rules specification version (`1`). |
| `name` | Catalog and UI | Human-readable rule set name. |
| `description` | Catalog and UI | Rule set description. |
| `commits` | `commit-msg` hook, `evin/changelog@v1`, `evin/version-bumper@v1` | Conventional commit message syntax and validation. |
| `branches` | `pre-push` hook, developer workflow | Branch naming format and push safety. |
| `releases` | `evin/version-bumper@v1`, `evin/changelog@v1`, `evin/git-release@v1` | Semantic bump mappings, changelog categories, and package policies. |
| `tags` | `pre-push` hook | Tag naming formats and deletion restrictions. |
| `pull_requests` | CI pipelines | Pull request title formats and governance rules. |
| `authorship` | `pre-commit` hook | Author email allowlists and cryptographic signature enforcement. |
| `history` | `commit-msg`, `pre-commit` | Linear history requirements, staged file size caps, and secret content blocks. |
| `files` | `pre-commit` hook | File naming conventions, required license headers, and blocked paths. |
| `lfs` | `pre-commit` hook | Git LFS tracking rules for binary assets. |
| `submodules` | `pre-commit` hook | Submodule creation permissions and allowed host lists. |
| `remotes` | `pre-push` hook | Allowed push remote destinations and force-push protection. |
````

## Commit and branch namespaces

````lsp
target: [GitRules, commits]
language: flow
title: Commit message rules
synopsis: "commits:\n  message_format:\n    - \"{type}({scope}?){breaking?}: {description}\"\n    - \"{type}: {description}\"\n  ignore_patterns: [\"^Merge branch\", \"^Revert\"]\n  fields:\n    type:\n      allowed_values: [feat, fix, docs, refactor, perf, test, chore]\n      must_be: lowercase-with-hyphens\n    description:\n      max_length: 72\n  policies:\n    require_body: false\n    max_body_line_length: 100\n    allow_empty_commits: false\n    require_ticket_reference: false"
summary: Enforce conventional commit syntax, allowable types, subject length, and commit policies.
category: configuration
---
Configures commit message formatting enforced by the `commit-msg` Git hook and parsed by changelog and version-bumper actions.

### Configuration Fields

- `message_format`: String or list of template patterns with named capturing groups (e.g. `{type}`, `{scope}`, `{breaking}`, `{description}`).
- `ignore_patterns`: Regex patterns bypassing validation (e.g. merge commits, reverts).
- `fields`: Field constraint mappings validating values, casing (`must_be: lowercase-with-hyphens`), allowed values, or regex patterns.
- `policies`: Operational rules such as `require_body`, `max_body_line_length`, `allow_empty_commits`, and `require_ticket_reference`.
````

````lsp
target: [GitRules, branches]
language: flow
title: Branch naming rules
synopsis: "branches:\n  name_format:\n    - \"{type}/{ticket}-{description}\"\n    - \"{type}/{description}\"\n  fields:\n    type:\n      allowed_values: [feat, fix, chore, docs, refactor, release]\n      must_be: lowercase-with-hyphens\n    description:\n      must_be: lowercase-with-hyphens\n  policies:\n    block_push_to_main: false"
summary: Validate branch naming formats, issue tickets, and push policies.
category: configuration
---
Governs branch name patterns and push protections evaluated at branch creation or `pre-push`.

### Features

- `name_format`: Single string or alternative templates defining structured branch naming conventions.
- `fields`: Constraints applied to placeholder variables in the branch name.
- `policies.block_push_to_main`: Prevents direct pushes to the default branch (`main` or `master`).
````

## Releases and distribution

````lsp
target: [GitRules, releases]
language: flow
title: Release rules
synopsis: "releases:\n  versioning:\n    strategy: cargo\n  change_types:\n    feat:\n      bump: minor\n      changelog_section: Features\n    fix:\n      bump: patch\n      changelog_section: Bug Fixes\n  commit_message: \"chore(release): {version}\"\n  policies:\n    breaking_change_bump: major\n    pre_release_prefix: rc\n  prerelease:\n    channels:\n      canary: \"canary.{n}\"\n      beta: \"beta.{n}\"\n  changelog:\n    ticket_linking:\n      prefix: \"EVIN-\"\n      url_template: \"https://jira.example.com/browse/{ticket}\"\n  packages:\n    app:\n      watch: [crates/app/**]\n      targets: [deb, apk, arch]"
summary: Define semantic version bump rules, changelog categories, ticket links, and distribution package policies.
category: configuration
---
Defines how commit types impact semantic versioning, how changelog sections are organized, and how distribution packages are tracked.

### Key Sections

- `change_types`: Maps commit types (`feat`, `fix`, `docs`, etc.) to bump levels (`major`, `minor`, `patch`, `none`) and changelog section headings.
- `versioning.strategy`: Selects `semver` (default) or `cargo` impact-to-version mapping.
- `commit_message`: Template used by release actions when generating release commits.
  The changelog action also skips commit subjects matching this template; it
  does not hide other commits of the same type.
- `policies`: Breaking change bump defaults and prerelease prefixes.
- `prerelease.channels`: Prerelease versioning patterns (`canary.{n}`, `beta.{n}`, `{git.branch}.{n}`).
- `changelog.ticket_linking`: Automatically transforms issue IDs matching `prefix` into markdown links using `url_template`.
- `packages`: Declares package policy identifiers, monitored file paths (`watch`), and target distribution formats (`targets`).
````

````lsp
target: [GitRules, releases, versioning, strategy]
language: flow
title: Versioning strategy
synopsis: "strategy: cargo"
summary: Choose the release impact-to-version mapping.
category: configuration
---
`semver` is the default. `cargo` maps minor impacts to patch increments and
major impacts to minor increments below 1.0.0.
````

## Git hooks, safety, and security

````lsp

Configures tag validation rules enforced during `pre-push`.

### Options

- `name_format`: Format pattern required for Git tags (e.g. `v{version}`).
- `policies.require_annotated`: Requires annotated Git tags with messages rather than lightweight tags.
- `policies.block_deletion`: Blocks deletion of remote tags during push.
````

````lsp
target: [GitRules, authorship]
language: flow
title: Commit authorship rules
synopsis: "authorship:\n  allowed_emails: [\"*@company.com\"]\n  policies:\n    require_signatures: false\n    block_identity_forging: false"
summary: Validate author email addresses, require GPG/SSH signatures, and block identity forging.
category: configuration
---
Enforces commit author verification during `pre-commit`.

### Options

- `allowed_emails`: Glob patterns or exact email addresses permitted as commit authors.
- `policies.require_signatures`: Enforces cryptographically signed commits (GPG, SSH, or S/MIME).
- `policies.block_identity_forging`: Verifies that the Git committer matches the configured Git user identity.
````

````lsp
target: [GitRules, history]
language: flow
title: History integrity and secret scanning
synopsis: "history:\n  content_blocks:\n    - pattern: \"(?i)AKIA[0-9A-Z]{16}\"\n      error_message: \"AWS Access Key ID detected\"\n    - pattern: \"-----BEGIN PRIVATE KEY-----\"\n      error_message: \"Private Key detected\"\n  policies:\n    require_linear_history: false\n    max_staged_file_size: \"50MB\""
summary: Scan staged commits for secrets, enforce linear history, and cap staged file sizes.
category: configuration
---
Enforces repository safety checks before commits are finalized.

### Features

- `content_blocks`: Scans staged changes against regex patterns to detect and block credentials, private keys, or API tokens.
- `policies.require_linear_history`: Disallows merge commits to maintain a clean linear commit graph.
- `policies.max_staged_file_size`: Rejects commits containing large files (e.g. `"50MB"`) that should be tracked in Git LFS instead.
````

````lsp
target: [GitRules, files]
language: flow
title: File naming and content rules
synopsis: "files:\n  naming_convention: snake_case\n  ignore: [target/**, vendor/**]\n  content_rules:\n    - name: \"rust-license-header\"\n      include: [\"*.rs\", \"**/*.rs\"]\n      exclude: [target/**]\n      require_pattern: \"(?m)^// Copyright \\\\(C\\\\)\"\n      error_message: \"Rust source file missing license header\"\n  policies:\n    block_paths: [\".env.production\", \"secrets/**\"]"
summary: Enforce file naming conventions, license headers, and blocked file paths.
category: configuration
---
Scans staged files during `pre-commit` to ensure codebase consistency and compliance.

### Features

- `naming_convention`: Enforces casing standards (`snake_case`, `kebab-case`, `camelCase`).
- `content_rules`: Inspects matching files for mandatory regex patterns (`require_pattern`) or forbidden patterns (`forbid_pattern`).
- `policies.block_paths`: Explicitly forbids committing sensitive paths (such as `.env` files or credentials).
````

````lsp

category: configuration
---
Ensures large binary assets are managed with Git LFS during `pre-commit`.

### Options

- `require_tracking_for`: List of file extensions that must be tracked via `.gitattributes` under Git LFS.
- `require_lfs_installed`: Verifies that the Git LFS binary is present and initialized in the local environment.
````

````lsp

language: flow
title: Git remote push rules
synopsis: "remotes:\n  policies:\n    allowed_push_remotes: [origin]\n    block_force_push: [main, master, release]\n    require_up_to_date: true"
summary: Restrict push destination remotes, block force-pushing to protected branches, and require up-to-date refs.

Enforces push safety during `pre-push`.

### Options

- `allowed_push_remotes`: Whitelist of remote names to which pushes are allowed.
- `block_force_push`: List of branch names protected against destructive force-push operations (`--force`).
- `require_up_to_date`: Requires fetching and rebasing/merging remote changes before pushing.
````

## Root namespaces overview

```flow
#!evin/v1
version: 1
name: Repository standard
description: Rules shared by local hooks and release actions.

commits: {}
branches: {}
releases: {}
authorship: {}
history: {}
tags: {}
pull_requests: {}
files: {}
lfs: {}
submodules: {}
remotes: {}
```

| Namespace | Primary consumer |
| --- | --- |
| `commits` | `commit-msg`, changelog parsing, and version calculation |
| `branches`, `tags`, `remotes` | `pre-push` |
| `files`, `lfs`, `submodules`, `authorship` | `pre-commit` |
| `history` | Staged-file size/content checks and `commit-msg` history integrity |
| `releases` | Version bumper, changelog, and Git release actions |
| `pull_requests` | Accepted policy metadata; no local Git hook currently receives PR metadata |

The root struct supplies defaults for omitted namespaces. Unknown fields are
rejected.

## Commit and branch formats

`message_format`, `name_format`, and `title_format` accept one template string
or a list of alternatives. Named placeholders become fields that constraints
can validate.

```flow
commits:
  message_format:
    - "{type}({scope}?){breaking?}: {description}"
    - "{type}: {description}"
  ignore_patterns: ["^Merge branch", "^Revert"]
  fields:
    type:
      allowed_values: [feat, fix, docs, refactor, test, chore]
      must_be: lowercase-with-hyphens
    description:
      max_length: 72
  policies:
    require_body: false
    max_body_line_length: 100
    allow_empty_commits: false
    require_ticket_reference: false

branches:
  name_format:
    - "{type}/{ticket}-{description}"
    - "{type}/{description}"
  fields:
    type:
      allowed_values: [feat, fix, docs, chore]
  policies:
    block_push_to_main: false
```

A field constraint accepts `must_be`, `allowed_values`, `pattern`, and
`max_length`. Optional placeholders use `?` in the format template.

## Release calculation

```flow
releases:
  versioning:
    strategy: cargo
  change_types:
    feat:
      bump: minor
      changelog_section: Features
    fix:
      bump: patch
      changelog_section: Bug Fixes
    docs:
      bump: none
      changelog_section: Documentation
  commit_message: "chore(release): {version}"
  policies:
    breaking_change_bump: major
    pre_release_prefix: rc
  prerelease:
    start_at_one: false
    channels:
      canary: "canary.{n}"
      branch: "{git.branch}.{n}"
  changelog:
    ticket_linking:
      prefix: "EVIN-"
      url_template: "https://tracker.example/{ticket}"
    host_integration: null
  packages:
    evin:
      watch: [Cargo.lock, crates/evin/**, .evin/packages.flow]
      targets: [deb, apk, arch]
      revision:
        scope: package
```

`bump` is `major`, `minor`, `patch`, or `none`. `versioning.strategy` is
`semver` by default or `cargo` for Cargo-compatible pre-1.0 versioning,
which interprets minor impacts as patch increments and major impacts as minor
increments. The old action option `cargo_pre_1_0` is rejected; migrate it to
this Git rule. See the
[version-bumper reference](/reference/actions/version-bumper-action). Channel
templates may use `{n}`, `{workspace.name}`, `{git.branch}`, `{git.short_sha}`,
`{date.ymd}`, and `{env.NAME}`. `evin/git-release@v1` uses
`releases.commit_message` when its own `message` field is absent.

Package IDs use lowercase letters, digits, and hyphens. `watch` contains safe
workspace-relative globs and may not select `.evin/release-lock.yaml`.
`targets` is a non-empty unique subset of `deb`, `apk`, and `arch`; revision scope is
`package` by default or `target`. GitRules remains policy-only—the version
bumper is the normal writer of the tracked release lock.

## Files and repository safety

```flow
history:
  content_blocks:
    - pattern: "-----BEGIN PRIVATE KEY-----"
      error_message: "Private key detected"
  policies:
    require_linear_history: false
    max_staged_file_size: 50MB

files:
  naming_convention: null
  ignore: [vendor/**]
  content_rules:
    - name: rust-license-header
      include: ["*.rs", "**/*.rs"]
      exclude: [target/**]
      require_pattern: "(?m)^// Copyright \\(C\\)"
      forbid_pattern: null
      error_message: "Rust source file missing its license header"
  policies:
    block_paths: [.env.production]

lfs:
  policies:
    require_tracking_for: [.psd, .mp4, .zip]
    require_lfs_installed: false

submodules:
  policies:
    allow_creation: false
    allowed_hosts: [github.com]
```

The `pre-commit` policy reads staged content, so checks apply to the proposed
commit rather than arbitrary unstaged working-tree files.

## Tag, authorship, and remote policies

```flow
tags:
  name_format: "v{version}"
  policies:
    require_annotated: true
    block_deletion: true

authorship:
  allowed_emails: []
  policies:
    require_signatures: false
    block_identity_forging: false

remotes:
  policies:
    allowed_push_remotes: [origin]
    block_force_push: [main]
    require_up_to_date: false
```

These policies are enforced at the hook where Git provides the necessary
state. For example, remote and ref information arrives at `pre-push`, while
author identity and staged files are checked at `pre-commit`.

## Synchronization and invocation

`evin sync` installs `pre-commit`, `commit-msg`, and `pre-push` even when no
task is bound, because those hooks carry policy enforcement. Tasks can be
attached independently through `on.hooks`.

Generated hooks use the installed `evin` command unless the workspace defines
`hook_runner`:

```flow
workspace:
  name: source-checkout
  version: "1.0.0"
  hook_runner:
    command: cargo
    args: [evin-dev]
```

The shim changes to the Git repository root, shell-quotes the command and each
argument, then appends `run <hook-name> -- <git-arguments>`.

> [!CAUTION]
> Setting a namespace to custom values changes both hook behavior and release
> interpretation. Test policy changes with `evin sync --dry-run --verbose` and
> manually run the relevant hook target before relying on it in CI.
